# Architecture — Aliob (package `birr5`, Android app "5BIRR")

This file documents the **current real state** of the system, generated by
reading the live code and migrations (October 2026). The migration-by-migration
history and the deeper "why" live in `docs/ARCHITECTURE.md` and in the header
comment of every migration file; this file is the map.

Stack: **Flutter** (Android-first, signed release AAB) + **Supabase**
(Postgres with RLS, Storage, Edge Functions on Deno) + **Riverpod** +
**go_router**. CI on **GitHub Actions**.

---

## 1. Database schema overview

### Identity and roles

| Table | Role |
|---|---|
| `profiles` | Every end user. `status` ∈ `account_status` (`PENDING_APPROVAL, APPROVED, REJECTED, SUSPENDED, INACTIVE`), synced from provider status by `trg_sync_profile_status`. |
| `provider_profiles` | A trading account. `provider_type` ∈ (`SERVICE_PROVIDER`, `VEHICLE_PROVIDER`), same `status` enum, `registration_fee_paid` (the one-time activation fee), `referred_by_staff_id` (staff-assisted signup), business fields + GPS. One per `user_id`. |
| `staff` + `staff_permissions` | Sub-admins/staff with a permission set (registration oversight, document review, etc. — `20260922000010`). |

`app_role` enum (`USER, VEHICLE_PROVIDER, SERVICE_PROVIDER, ADMIN`) labels the
auth identity; the authoritative trading state lives in the two tables above.

### Marketplace

- **`categories`** — self-referencing `parent_id` (the "mother category"
  hierarchy; a product may sit on a mother or any of its children), `sector`
  ∈ (`SERVICE`, `VEHICLE`), optional `marketplace_sector`
  (FOOD/RETAIL/ACCOMMODATION/SERVICES/TRANSPORT/OTHER), `is_active`.
  Admin-managed from `/admin/categories` + `/admin/category-fields`
  (per-category custom fields), with per-category/city fees in the fee tables
  (see §6).
- **`products`** — `provider_id`, `category_id`, `listing_type`
  ∈ (`PRODUCT, FOOD, SERVICE, ROOM, OTHER`), `listing_status`
  ∈ (`ACTIVE, DRAFT, SOLD_OUT, ARCHIVED`) default `ACTIVE`, `is_active`
  default true, `price` = the **provider's own raw price**, `display_price`
  = the public price (GENERATED — see §6), `price_per_unit`/`unit`
  (KG/LTR), `requires_availability_confirmation`, `city` (null = all cities),
  `location` (geography point; null = excluded from proximity ranking),
  `like_count`/`dislike_count`, `sales_count`.
- **`product_images`** — `product_id`, `storage_path` in the private
  `product-images` bucket (object path MUST start with the owner's auth uid —
  every write policy scopes `storage.foldername(name)[1] = auth.uid()`),
  `sort_order`.
- **`vehicles`** — provider fleet for the ride side; `status`
  `PENDING_APPROVAL` on create.
- **`product_reactions`** — like/dislike per user per product, written via the
  idempotent `set_product_reaction` RPC.
- **`provider_stores`** — the provider's public gallery page data.

### Orders, payments, wallet

- **`orders`** — 12-state machine (see §4). `order_number` for humans.
- **`availability_requests`** — the pre-payment "does this exist?" queue
  (see §4); answered by the provider **or** an admin
  (`20261014000004`).
- **`wallets`** + **`wallet_transactions`** (`TRANSACTION_FEE,
  SUBSCRIPTION_FEE, DEPOSIT, WITHDRAWAL, ADJUSTMENT, REFUND`) — one wallet per
  provider; the platform withholds its per-order fee and the monthly
  subscription from here.
- **`recharges`** — admin-mediated wallet top-ups: buyer/admin uploads a
  payment screenshot, an admin approves (`PENDING/APPROVED/REJECTED`).
- **`order_payment_screenshots`** — buyer's payment proof per order
  (`20260929000001`), verified by admin before contacts are released.
- **`system_settings`** — key→JSONB settings, self-modification blocked by
  trigger: fee switches, `posting_min_wallet_balance`, `posting_fee`,
  `enforce_verified_documents`, `allow_negative_wallet`, platform contact +
  payment account (`20261014000003`).

### Registration, verification, support

- **`captcha_challenges`** — signup CAPTCHA (`20260924000003`), solved
  challenges preserved (`20260924000010`).
- **`user_documents`** — ID uploads; `verification_status` default
  `MANUAL_REVIEW`; `AUTO_APPROVED/VERIFIED` pass the strict server gate.
- **`approval_requests`** — provider/user approval audit trail.
- **`notifications`** — in-app panel + FCM push (`0007`, `20260927000058`,
  `20261015000001`); "welcome on approval" via `notify_user_once`.
- **`appeals`/disputes, `support_tickets`, `terms`** — buyer problem reports
  reach the admin queue from the transaction itself; support tickets
  (`0039`).
- **`ride_requests`** — the ride flow (§4), deliberately separate.

RLS is enabled on every table; public discovery reads go through
`SECURITY DEFINER` functions (`search_products`,
`visible_products_for_city`, `ranked_providers`) and, since
`20261020000001`, guests browse as **anon** with narrowly-scoped anon
policies. Client write protection is defended by triggers
(`20260927000019`, `20260927000040`).

## 2. Registration paths

1. **Self-service user** — guest taps a transaction →
   `requestAccountToContinue` dialog → `/signup/user`. Signup requires the
   CAPTCHA and the Privacy Policy checkbox (and OTP when the
   `signup_otp_required` toggle is on). Account is active immediately.
2. **Self-service provider** — `/signup/service`, no valid staff referral
   code: `handle_new_user` creates the `provider_profiles` row **born
   APPROVED** plus its wallet and subscription rows
   (`20261014000000`). Documents are **voluntary**
   (`20261014000001` — service providers are never blocked by
   `DOCUMENTS_UNVERIFIED`; vehicle providers still are). To trade they pay
   the one-time activation fee (admin-mediated payment proof) and hold the
   admin's wallet minimum — enforced by `provider_fulfilment_blockers()`.
3. **Staff-assisted provider** — a staff member signs the provider up with a
   valid, active **staff referral code**: `referred_by_staff_id` is set and
   the row stays `PENDING_APPROVAL` until an admin approves the uploaded
   documents (`approve_provider`). The two paths cannot cross: an unknown or
   blank code is ordinary self-service.

**Guest mode** — "Continue as guest" sets an in-memory flag
(`GuestSession`/`guestModeProvider`); reads run as anon. Transaction routes
(`/user/availability`, `/user/checkout`, `/user/payment`, `/user/order-waiting`,
`/user/ride-request`, `/documents`, `/review`, anything under `/user/orders`)
redirect to `/signup/user`; account routes (`/admin*`, `/staff*`, `/wallet*`,
`/account/*`, …) to `/login`. Dialog interception sits on every transactional
CTA (Buy/Book `ProductBuyButton`, add-to-cart, checkout, ride request on home
and map, favorites).

## 3. Client architecture (short)

- `lib/main.dart` → `lib/core/bootstrap.dart` (Supabase + Firebase init,
  update gate) → `lib/app.dart` (ProviderScope, theme, router).
- `lib/routing/app_router.dart` — go_router with the auth+guest redirector.
- `lib/core/services/` — one service per server concept
  (`fee_resolver`, `posting_gate`, `provider_readiness`, `cart_service`,
  `wallet_service`, `platform_settings_service`, `guest_session`, …).
- `lib/core/resilience/` — `AppFailure` + `AppFailureMapper`
  (`friendly_error.dart` is the screen-facing wrapper), `safeCall`, and the
  app-wide rule: **no raw exception text ever reaches a screen**.
- `lib/core/widgets/` — shared UI: `ProductCard` (the one listing card;
  `BoxFit.contain` + cached image with spinner/error fallback — no crop),
  `ProductBuyButton`, `AsyncView`/`LoadErrorView` (the shared
  loading/error pattern), `PrimaryButton` (has `isLoading`), banners, sheets.
- Every screen doing async work shows a spinner while waiting and a friendly
  message on failure (enforced by review + the harness; §8).

## 4. Lifecycle state machines

### Orders (products **and** delivery — one machine)

`order_status`: `CREATED → PENDING_PROVIDER → ACCEPTED → PAYMENT_PENDING →
PAYMENT_VERIFICATION → APPROVED → STARTED → COMPLETED`, plus
`CANCELLED / REJECTED / DISPUTED / REFUNDED`.

Flow: `ProductBuyButton`/checkout adds to cart → the **availability gate**
(`/user/availability`): if the listing has
`requires_availability_confirmation`, a row lands in `availability_requests`
and the buyer sees NO payment details until the provider (or an admin —
`20261014000004`) answers YES (`create_order_secure` demands the same answer
server-side). On YES the order unlocks the provider's payment account and the
screenshot upload together; the buyer pays to the **platform account** and
uploads proof → `PAYMENT_VERIFICATION` → admin verifies →
contacts + GPS release (`20261006000009`, no contact before payment) →
`STARTED → COMPLETED`. At completion the platform's per-order fee is withheld
from the provider's wallet (`wallet-deduct-fee` / charge resolvers). A buyer
can open an appeal/dispute from the order; it lands in the admin queue.
Sold listings are hidden, not deleted (`20261015000003`).

**Subscription** — `charge_due_subscriptions()` runs monthly; an unpaid fee
sets `provider_profiles.status = 'SUSPENDED'` (carried to `profiles.status`),
which the router turns into the suspended screen. Recharging renews.

### Rides (separate, unchanged)

`ride_status`: `REQUESTED → CLAIMED → DRIVER_ARRIVING → STARTED →
COMPLETED/CANCELLED`. A rider requests from home/map → the ride reaches the
database and expires (`20261006000005`) → a **vehicle** provider with
verified documents (`claim_ride` enforces the fulfilment gate) claims it via
`ride-claim`/`ride-transition`. The ride fare IS the delivery fee. This flow
is deliberately untouched by the service-provider registration rework.

## 5. Publishing gate (what makes a listing go live)

Server-side, one function: **`provider_fulfilment_blockers(provider_id)`**
(20261014000001 version) returns
`ACCOUNT_NOT_APPROVED | SUBSCRIPTION_UNPAID | ACTIVATION_FEE_UNPAID |
DOCUMENTS_UNVERIFIED (vehicle providers only) | WALLET_EMPTY |
WALLET_BELOW_MINIMUM`; empty array = may trade. `create_provider_product`
and `create_provider_vehicle` refuse with the reason-carrying code
`PROVIDER_NOT_FULFILMENT_READY`, translated by `friendly_error()`.

A new listing needs **no admin approval**: `listing_status` defaults
`ACTIVE`, `is_active` defaults true, and photo-less listings are simply
private to discovery (`20261011000001` — `search_products` and
`visible_products_for_city` require a `product_images` row; the provider's own
page still shows text-only listings). Images upload straight from the form to
`product-images/{uid}/{productId}/…` and the card renders them cached with
`BoxFit.contain` (no crop).

The client mirrors this with `PostingGate`/`ProviderReadiness`, which **read**
`provider_fulfilment_blockers()` instead of re-deriving the rule, and the
product form opens the document sheet only when the server says documents
block that provider.

## 6. Pricing — the single source of truth

`products.display_price` is a **STORED GENERATED** column
(`20261014000002`):

```
display_price = price + 5 + price × 0.019     # flat 5 ETB + 1.9% margin
```

The arithmetic exists exactly once — in the table. `price` stays the
provider's own number (shown only on provider screens); every public surface
(home, search, trending, gallery, category, cart, checkout, product page) and
the order pricer (`order-create` Edge Function) read `display_price`. No
screen and no RPC recomputes the formula.

Per-category/city fee knobs (commission %, listing fee, activation fee,
delivery fee) live in the fee tables + `system_settings`, resolved by the
shared client `FeeResolver` for previews and by the matching server charge
resolvers for the actual charge — same numbers both sides.

| Function | What it does |
|---|---|
| `order-create` | Authoritative order creation + pricer (accepts product + qty only; charges `display_price`). |
| `order-transition` | Order status machine; releases contact/GPS at the right step. |
| `ride-claim` / `ride-transition` | Ride lifecycle (vehicle providers only, doc-verified). |
| `subscription-process` | Monthly subscription charging → suspension. |
| `wallet-deduct-fee` | Platform fee withholding at completion. |
| `admin-wallet-recharge` | Admin-mediated wallet recharge. |
| `provider-approval` | approve/reject/suspend providers (+ welcome notification). |
| `document-verify` | QR-capable ID verification (auto-approve). |
| `send-otp` | Signup/login OTP (toggled by `signup_otp_required` / `otp_bypass`). |
| `login-gate` | CAPTCHA/OTP-gated login. |
| `staff-login`, `staff-create-gateway`, `staff-delete-gateway`, `staff-change-password`, `account-change-password` | Staff & password doorways. |
| `password-reset-gateway`, `account-deletion-gateway` | Reset & deletion (with terms). |
| `user-admin`, `admin-image-delete` | Admin user actions & image cleanup. |
| `index-chunks`, `repo-chat`, `_shared` | Support/internal utilities. |

## 8. Admin surface (`/admin` dashboard)

Every admin-controllable area from all rounds has a dashboard entry (verified:
every `context.push` target in `lib/` resolves to a real route):

- **Marketplace** — orders, availability request queue
  (`/admin/availability`; admin may answer requests too), payment
  verification (`/admin/order-payments`), transactions history, disputes,
  appeals.
- **Catalogue** — categories incl. mother-category wiring
  (`/admin/categories`), per-category fields (`/admin/category-fields`),
  fees (`/admin/fees`, `/admin/fees/categories`).
- **People** — providers, users, approvals, **staff-assisted registration
  oversight** (`/admin/registrations`), document verification, staff &
  sub-admin management (`/admin/staff`, `/admin/staff-assignment`,
  `/admin/roles/permissions`), deletions, accounts.
- **Money** — payment accounts + payment methods, platform contact & payment
  settings (`/admin/platform-settings?section=contact|payment`), expenses,
  income, reports, admin wallet recharges.
- **Platform** — settings, send notifications, support tickets, app releases.

## 9. CI/CD (`.github/workflows/`)

- **`flutter-ci.yml`** — on push to `main` and every PR: `pub get` →
  format check → `flutter analyze --no-fatal-infos --no-fatal-warnings`
  (errors block) → `flutter test` → the repo harness
  (`tools/harness/run_all.sh`, 71 static + migration gates) → commit
  `pubspec.lock` if changed → decode the release keystore → **build the
  signed release AAB only** (the debug-APK build was removed for Actions
  minutes) → upload `release-aab-<version>` artifact (14-day retention).
  Secrets: `KEYSTORE_BASE64`, `KEYSTORE_PASSWORD`, `KEY_PASSWORD`,
  `KEY_ALIAS`, `SUPABASE_URL`, `SUPABASE_ANON_KEY`, `GOOGLE_MAPS_API_KEY`.
- **`build.yml`** — dispatch-only standalone release AAB (never a side
  effect of a push).
- **`connectivity-ci.yml`** — PRs touching `supabase/**` or
  `tools/integration_test/**`: throwaway local Supabase stack, applies all
  migrations, runs the live connectivity suite. Needs
  `SUPABASE_ACCESS_TOKEN`, `SUPABASE_PROJECT_REF`, DB credentials.
- **`deploy-supabase.yml`** — push to `main` touching `supabase/**` (or
  dispatch): `supabase db push` of `supabase/migrations`, then dispatches
  the app-build repo.

Versioning: `pubspec.yaml` `version: X+build` is stamped into artifact
names; bump the build number on every release so bundles are tellable apart.

## 10. Verification harness

`tools/harness/run_all.sh` runs ~71 checks (`tools/harness/static_checks.py`
+ migration gates + `tools/integration_test/`) over the Dart, the SQL and the
migrations a deploy would actually apply — including checks that the posting
gate is wired, that `friendly_error()` recognises every refusal code the
server can raise, that guest gates stay on every transaction CTA, and that a
restatement cannot silently drop a pinned rule. CI runs it on every push.
